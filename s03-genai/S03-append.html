Nombre del marco

Framework de arquitectura de agentes

Es un mapa de responsabilidades: cada capa resuelve un problema distinto y puede implementarse con productos diferentes. No es una lista de productos ni obliga a usar un único proveedor.

Diseño

Separa responsabilidades

Permite decidir dónde vive el canal, el modelo, la recuperación, las herramientas y la seguridad.

Portabilidad

Reduce el lock-in

Los contratos y las interfaces pueden mantenerse aunque cambie Foundry, Databricks u otro runtime.

Operación

Hace visibles los gaps

Un prototipo puede responder bien y aun así no tener observabilidad, guardrails o control de acceso.

Arquitectura agnóstica de agentesS03 · contexto

El mapa completo

Un agente se diseña en nueve capas

01 · Canal y experienciaWhatsApp, Jira, Teams, portal o API; conversación y UX.
02 · Entrada y normalizaciónRecibir, validar esquema, limpiar y convertir el evento.
03 · Borde, seguridad y gatewayAutenticación, rate limit, APIM, IP allowlist y secretos.
04 · Clasificación y ruteoDetectar intención, dominio, prioridad y siguiente capacidad.
05 · Recuperación / groundingBuscar evidencia en documentos, vectores, SQL o funciones.
06 · Razonamiento y decisiónInterpretar contexto, planificar y seleccionar una respuesta o acción.
07 · Validación y guardrailsSeguridad, política, formato, groundedness y aprobación.
08 · Acción y herramientasMCP, APIs, funciones, escritura y escalamiento humano.
09 · Observabilidad, evaluación y mejoraLogs, trazas, costo, calidad, feedback y regresiones.

S03 · qué queda demostradoFramework de 9 capas

Arquitectura de referencia

El flujo de referencia separa canal, agente y datos

01Canal: una app, portal, chat o API recibe la solicitud y el gateway aplica el borde de seguridad.
02Entrada: el adaptador valida, normaliza, reintenta y evita duplicados antes de invocar al agente.
03Agente: un runtime de agentes coordina prompt, identidad, razonamiento y herramientas.
04Conocimiento: una plataforma de datos expone fuentes gobernadas, búsqueda, SQL y funciones.
05Salida: se aplican guardrails, se registra telemetría y se responde al canal original.
El pod no debe convertirse en una caja mágica: cada responsabilidad tiene una capa, un contrato y una evidencia.

Criterio de diseño

La frontera importante no es el proveedor: es la responsabilidad

Verdad

Databricks decide el dato

El ranking, las reglas, los agregados y las funciones deterministas deben permanecer auditables.

Inteligencia

Foundry decide cómo actuar

El agente interpreta la solicitud, elige herramientas permitidas y redacta la respuesta.

Contrato

La interfaz desacopla

Una tool bien definida permite cambiar el backend sin reescribir la experiencia completa.

Regla para el curso: el LLM puede explicar una decisión basada en datos; no debe inventar el dato ni sustituir una regla de negocio.

Actividad final

Ubica cada pieza antes de construir

Para un agente de soporte, señala qué componente implementarías en cada capa y qué evidencia demostraría que funciona.

Pregunta 01

¿Dónde entra?

¿Qué canal, gateway y contrato recibe el evento?

Pregunta 02

¿Dónde sabe?

¿Qué fuente recupera, quién la gobierna y cómo se valida?

Pregunta 03

¿Dónde actúa?

¿Qué tool puede ejecutar, con qué permiso y qué traza deja?

Cierre: una demo de chatbot muestra una respuesta; una arquitectura de agente demuestra un sistema completo.
